# DoW Replay Analyzer

*Читать на других языках: [English](README.md)*

Java-инструмент, который разбирает реплеи **Dawn of War** (`.rec`) и восстанавливает действия каждого игрока — порядок построек, захваты точек, приказы юнитам, способности и сводную стратегическую статистику — напрямую из бинарного потока команд.

Формат реплея недокументирован, поэтому поток команд был реверс-инжинирен побайтово. Этот проект — результат той работы.

> ⚠️ Неофициальный инструмент, полученный реверс-инжинирингом. Не связан с Relic Entertainment или SEGA. Читает собственную копию байтов реплея и никогда не изменяет файл.

---

## Что он делает

По файлу `.rec` анализатор печатает структурированный отчёт:

- **Заголовок** — карта, длительность (тики → секунды), список игроков и наблюдателей.
- **Сводка по потоку команд** — сколько событий разобрано, пакетов прочитано, sub-команд декодировано.
- **Найденные CMD_ID** — все встреченные опкоды команд с их счётчиками.
- **Таймлайн** — хронологический список декодированных событий (тик, время, команда, entity, позиция).
- **События построек / захватов / генераторов** — отфильтрованные срезы по зданиям и захватам точек.
- **Таймлайны по игрокам** — события, разделённые между двумя живыми игроками.
- **Порядок построек (build order)** — ключевые экономические и стратегические действия каждого игрока по порядку.
- **Стратегический анализ** — экономика (барак, генераторы, посты ЛП, захваты, тех) и армия (приказы, атаки, способности) по каждому игроку.

## Как это работает

Файл `.rec` — это контейнер Relic Chunky. Конвейер обработки:

1. `BinaryReader` — низкоуровневое чтение байтов в little-endian.
2. `RecursiveRelicChunkParser` + `RelicChunkNode` + `ChunkSearch` — обход дерева чанков и поиск метаданных (карта, игроки) и чанка **`FOLDINFO`**.
3. `CommandStreamParser` — поток команд начинается сразу после `FOLDINFO`. Этот класс декодирует его в список `GameEvent` и привязывает каждое событие к игроку.
4. `test.Main` — точка входа; запускает конвейер и печатает отчёт.

### Структура потока команд (восстановлено реверсом)

Поток — это плоская последовательность **пакетов**, каждый соответствует одному игровому тику одного игрока:

| Смещение | Поле | Примечание |
|---------:|------|------------|
| `-4`     | размер пакета | 4-байтный LE-префикс перед payload |
| `0`      | маркер `0x50` | признак командного пакета |
| `1..4`   | тик | uint32 LE; `тик / 8.0` = секунды |
| `13`     | число команд | сколько sub-команд в пакете |
| `25..28` | inner size | покрывает только **первый** блок sub-команд |
| `30+`    | sub-команды | первый блок здесь; последующие достаются tail-сканом |

Каждая **sub-команда** несёт id сущности (`+2..5`), байт фазы на `+27` и — для 40-байтной формы — позицию (`x@+34`, `y@+36`, `z@+38`, int16 LE) и байт типа (`+10`, см. ниже). Размеры sub-команд:

- `28 / 33 / 35` — маркеры прогресса / завершения (без координат).
- `40` — реальная установка / приказ с координатами.
- `45` — составная команда, вкладывающая несколько опкодов.

Опкод (`cmd_id`) читается на `+29` для 40-байтных команд и на `+23` для остальных; 40-байтная форма постройки с фазой `3` кодирует тип как `0xC300 | byte[28]`.

### Атрибуция игрока: кластеризация по entity-id

У каждого игрока свой непрерывный, непересекающийся диапазон entity-id. Если отсортировать все entity-id, встреченные в реплее, и найти один доминирующий разрыв между соседями (в 5+ раз больше следующего по величине) — поток чисто делится на двух игроков. Это **реальный структурный сигнал**, а не эвристика, и он основной способ атрибуции для реплеев 1×1. Откат на старую эвристику (расово-эксклюзивные семейства команд + позиция домашней базы + пропагация по ближайшим соседям) происходит только когда чёткого бимодального разрыва нет — например, в мульти-слотовых лобби или реплеях с большим числом наблюдателей.

### `buildSubType`: настоящий id чертежа

Байт `+10` у 40-байтной команды (`GameEvent.buildSubType`) оказался **общим для движка id чертежа**, а не привязанным к конкретному `cmd_id`. Сверка 68 реплеев по 9 расам показала:

- `buildSubType == 0` в подавляющем большинстве 40-байтных команд — это **шум от движения/формации юнитов**, а не постройка: координаты плавно «шагают» тик за тиком, entity-id каждый раз новый (отдельные юниты в движущемся отряде), переиспользуя тот же формат, что и реальные постройки. У настоящих построек/produce-заказов `buildSubType` всегда `> 0`.
- `204` = первое произв. здание T1 (~раз за игру), `208` = здание типа «Пост ЛП» (повторяется по ходу игры), `209` = produce/rally-приказ — все три подтвердились с одинаковым смыслом у Space Marines, Dark Eldar и Sisters of Battle, то есть это, похоже, расово-нейтральные слоты движка, а не пораcовые коды.
- `90` — статистически сильный, но **неподтверждённый** кандидат на «Генератор» (повторяется ~2 раза/игру у пяти разных рас) — вынесен как эвристическая догадка, не факт.

`scr/test/DumpBuildTypes.java` — диагностический инструмент, которым собирались эти данные: выгружает каждое 40-байтное build-событие в CSV (`file,race,player,cmdId,buildSubType,tick,x,y,entity`) для кросс-реплейного анализа.

## Структура проекта

```
com.dow.replay.parser.BinaryReader              низкоуровневое чтение байтов
com.dow.replay.chunk.RelicChunkNode             узел дерева чанков

com.dow.replay.chunk.RecursiveRelicChunkParser  парсер Relic Chunky

```

## Сборка и запуск

Нужен JDK (собрано и проверено на JDK 21; JDK 17+ тоже должен подойти). Исходники в UTF-8.

В IntelliJ IDEA: откройте проект, выставьте SDK 17+ и запустите `test.Main`, передав путь к реплею как аргумент программы:

```
test.Main scr\replays\<replay>.rec
```

Из командной строки:

```bash
javac -encoding UTF-8 -d out $(find scr -name "*.java")
java -Dstdout.encoding=UTF-8 -cp out test.Main scr/replays/<replay>.rec
```

(`-Dstdout.encoding=UTF-8` нужен, чтобы кириллица и эмодзи в выводе не превращались в «?» на Windows-консолях.)

Имена файлов реплеев следуют схеме `W-<раса>-L-<раса>` (Winner / Loser), например `#1521554-W-ORK-L-TAU.rec` означает, что Орки победили, а Тау проиграли.

## Известные ограничения

Это честный реверс-инжиниринг недокументированного формата, и часть вещей в принципе не восстановима из одного только потока команд:

- **Записываются только команды, меняющие состояние.** Dawn of War пишет постройки, движение, атаки, способности, захваты и пополнения — но **не** выделения, движения камеры, нажатия групп управления и холостые приказы (основную массу «сырого» APM). Поэтому число команд намного ниже реального APM игрока — это by design.
- **Атрибуция игрока опирается на кластеризацию entity-id** (см. выше), что надёжно для стандартных реплеев 1×1. Откат на расо-позиционную эвристику происходит, когда чёткого разрыва кластеров нет (мульти-слот, много наблюдателей), и в этом резервном режиме общие команды (захват / движение / атака) всё ещё могут быть приписаны не тому игроку в окнах, где оба действуют попеременно.
- **Большинство семейств `cmd_id` общие для всех рас** — один и тот же диапазон опкодов встречается в матчах с совершенно разными парами рас, поэтому сам опкод редко однозначно указывает на расо-специфичное действие. Реальный тип постройки/юнита в основном живёт в `buildSubType` (байт `+10`, только у 40-байтных команд, см. выше), и подтверждено пока лишь несколько его значений — остальные печатаются как сырое `тип N`.
- **Стартовые базовые постройки бывают невидимы.** Часть ранних зданий ставится 28-байтными командами, которые сливаются с шумом завершения и не разводятся поштучно.
- **Команды ИИ / ботов не записываются** в поток команд реплея.
- **Наблюдатели** появляются как дополнительные слоты игроков (в 1×1 их может быть до 6), но команд не отдают.

## Статус

Активно реверсится. Атрибуция игрока и раскладка потока команд стабильны и перепроверены на 68 реплеях по 9 расам (Space Marines, Dark Eldar, Orks, Sisters of Battle, Tau, Imperial Guard, Necrons, Eldar, Chaos Space Marines). Декодирование оставшихся значений `buildSubType` в полные пораcовые названия построек/юнитов продолжается.
